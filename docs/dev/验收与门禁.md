# 验收与门禁

> 仓库的验收分成**四层**，各层回答不同的问题。别把某一层的绿当成另一层的证据 ——
> 「单测全绿」证明不了「接在界面上那条路真的跑了」，「CI 绿」也证明不了「真机上用户看得见」。
>
> 各脚本自己的用法不再复述：跑测试看 [CONTRIBUTING.md](../../CONTRIBUTING.md)，
> 真机脚本看 [scripts/verify/README.md](../../scripts/verify/README.md)。
> 门禁口径按**本仓库的** [.github/workflows/ci.yml](../../.github/workflows/ci.yml) 与
> [.github/workflows/release.yml](../../.github/workflows/release.yml) 写的（与上游不同，见
> [索引.md](索引.md) 的「与上游的差异」）。

---

## 一、四层各回答什么

| 层 | 回答的问题 | 载体 | 跑在哪 |
|---|---|---|---|
| ① 离线单测 | 纯逻辑对不对（不碰真设备 / 不联网） | [tests/](../../tests/)（脚本式，**不是 pytest**） | 本机 + CI 两腿 |
| ② CI 门禁 | 提交进得来吗（语法 / 静态 / 凭据 / 打包 / 平台隔离 / 文档链接） | [.github/workflows/ci.yml](../../.github/workflows/ci.yml) | GitHub runner |
| ③ 真机验收 | 功能在**真实环境**里跑通了吗 | [scripts/verify/](../../scripts/verify/) | 维护者本机（**不进 CI**） |
| ④ 发布复核 | 交付给用户的那个产物是不是对的 | [.github/workflows/release.yml](../../.github/workflows/release.yml) + [scripts/verify_release.py](../../scripts/verify_release.py) | tag 触发 + 本机复核 |

## 二、本地（提交前）

```bat
:: 全量：逐文件跑 tests/test_*.py（自动跳过需要真 key 的 test_engine.py），与 CI 同口径
.venv\Scripts\python.exe scripts\run_tests.py

:: 只跑名字含关键词的（子串或通配）
.venv\Scripts\python.exe scripts\run_tests.py --only i18n
.venv\Scripts\python.exe scripts\run_tests.py --only "test_room_*"

:: 附覆盖率摘要（不设阈值、不阻断）；--with-engine 连 test_engine.py 一起跑（要真 API key）
.venv\Scripts\python.exe scripts\run_tests.py --coverage
.venv\Scripts\python.exe scripts\run_tests.py --with-engine

:: 静态门禁（CI 里是阻断项）——只跑 F,E9 这一档，规则固化在 ruff.toml
.venv\Scripts\python.exe -m ruff check --select F,E9 .

:: 文档相对链接 / 锚点（**只加在 CI 的 Linux 腿**，本地先跑一次省一轮往返）
.venv\Scripts\python.exe scripts\check_doc_links.py

:: 凭据扫描（防 key 进历史）
.venv\Scripts\python.exe scripts\check_no_secrets.py --once
```

⚠️ 解释器**一律用仓库 venv**：本机与 CI 都**没有 `python3`**；裸 `python` 缺 `pythonosc` 等依赖，
会一大批用例秒红（看着像代码坏了）。

**本机两个具名放过**（别扩散到其它用例）：

| 用例 | 为什么放过 | 怎么确认它真不是代码坏了 |
|---|---|---|
| `tests/test_device_wasapi_filter.py` | 本机装着 Voicemeeter，设备表的实测假设与它冲突 | CI（干净 runner）恒绿 |
| `tests/test_tts_reuse.py` | 时序敏感，本机与别的东西抢资源时偶发 | 单独重跑 5/5 过、CI 恒绿 |

**跑之前先 `unset DASHSCOPE_API_KEY`**：用例里会 `os.environ.setdefault("DASHSCOPE_API_KEY", "sk-…")`
注入假 key，它会**顶掉**真凭据（解析顺序：配置 → 凭据存储 → 环境变量），
之后任何 `--self-test` / 复核都拿假 key 去连服务（`HTTP 401`），看着像**产物坏了**。
⚠️ 置空 ≠ 移除：`setdefault` 只在键**不存在**时生效。

## 三、CI 的门（四条腿）

触发：push 到 `main`、开/更新 PR、手动 `workflow_dispatch`。**推分支不会触发** ——
分支自己跑一遍要手动 `gh workflow run ci.yml --ref <分支>`。

| 腿（job） | runner | 跑什么 |
|---|---|---|
| `tests` | windows-latest | 装依赖 → 断言 Windows 独占依赖可导入（`openvr` / `pyaudiowpatch`）→ `compileall` → **ruff F,E9（阻断）** → `check_no_secrets.py --once` → 循环跑 `tests/test_*.py`（跳过 `test_engine.py`）+ 累积覆盖率摘要（非阻断） |
| `package` | windows-latest | `scripts/build_exe.py --no-verify` → 断言产物存在且体积正常 → **`check_platform_purity.py dist/VRChatLiveTranslate.exe --platform windows`**（产物里不许有 Linux 独占实现；含模块对账） |
| `linux-tests` | ubuntu-latest | 装系统依赖（xvfb / CJK 字体 / tk …）→ `compileall` → ruff → `check_no_secrets` → **`check_doc_links.py`** → `xvfb-run` 下跑同一批用例 |
| `appimage` | 复用 [.github/workflows/appimage.yml](../../.github/workflows/appimage.yml) | Linux 打包链路（含模块对账：磁盘上每个 `vlt/**.py` 都要在包里） |

三条注意：

- **文档链接检查只在 Linux 腿**：Windows 腿绿 ≠ 文档链接没问题。
- **AppImage 腿照跑**，即使本仓库**只发 Windows**：它守的是「Linux 代码没被我们改坏」与
  「平台禁列清单两边一致」。上游新增平台独占模块时，两份清单都要改（见
  [架构总览.md](架构总览.md) §六）。
- **CI 结论别取 `tail` 后的 `$?`**（管道里拿到的是 `tail` 的 0），也别说「PR checks 没报错」——
  PR 与 `main` 有冲突时 `pull_request` 触发的 CI **一次都不会跑**，`gh pr checks` 显示
  `no checks reported`。要结论用：
  `gh run view <id> --json jobs --jq '.jobs[] | "\(.name): \(.status)/\(.conclusion)"'`。

## 四、真机验收（③）

[scripts/verify/](../../scripts/verify/) 是**入库的**真机脚本（以前只在维护者本机的 `out/`，别人复现不了）。
它们不进 CI（需要真桌面会话 / Win32 能力 / 真虚拟声卡 / 联网），用途是**让验收可复现、让评审看得见**。

- 每份要什么硬件、会不会写盘、实测状态：[scripts/verify/README.md](../../scripts/verify/README.md)
- 约定：去硬编码路径、**只写 `out/` 或临时沙箱**、缺硬件时几秒内明确报错（禁 hang / 禁静默跳过）
- 临时的一次性探针脚本不要留在仓库里；能复用的验收脚本往 `scripts/verify/` 放
- 开箱即用冒烟（源码模式，假 HOME + 无 key + 无 config.yaml）：`out/smoke_fresh_install.py`
  —— ⚠️ `out/` 是 gitignore，这份脚本**不在仓库里**，只有本机有；发版前值得跑一次

## 五、发布与复核（④）

- [.github/workflows/release.yml](../../.github/workflows/release.yml)：推 `v*` tag 触发 →
  **对账 tag 与 `vlt/__init__.py` 的 `__version__`**（不一致直接失败）→ windows-latest 打单文件 exe →
  建 Release（`prerelease: false`、`generate_release_notes: false`），附件为 exe + `SHA256SUMS.txt`。
  **发版说明是手写在 workflow 里的 `body: |`**，每版必须亲自改（见 [索引.md](索引.md) 的差异表）。
- 复核产物：[scripts/verify_release.py](../../scripts/verify_release.py) —— SHA256 对账、**真跑
  `--self-test`**、版本行、字节码里搜新功能字符串（needle）、图标像素比对。
  needle 参数里放**本次改动独有的字符串**，否则复核证明不了「新代码在包里」；
  若本版应用零改动（只有脚本/CI/文档变），**沿用上一版那批 needle**，别临时编一个不存在的符号。
- 便宜且决定性的一条对账：`SHA256SUMS.txt`（工作流自己算）⟂ GitHub 服务端对资产算的
  `assets[].digest` —— 两者相等 ⇒「服务端收到的字节 == 工作流构建的那份」。
  取资产时**必须显式 `--repo <本仓库 slug> -p <文件名>`**：不带 `--repo` 时 `gh` 会按当前目录的
  `origin` 推断（本仓库的 `origin` 是**上游**）→ 下到上游同名 tag 的资产，看起来像发布事故。
  任何 hash 不一致，**先比尺寸**再下结论。
- 交付给用户的 exe **文件名必须纯 ASCII**（中文名会让 OpenVR 初始化直接失败）。

## 六、改动面 → 至少跑到哪一层

| 改动面 | 最低验证 |
|---|---|
| 纯文档 / 注释 | `scripts/check_doc_links.py`（+ 涉及 `.py` 时 `ruff`） |
| 词表 / 新增界面语言 | `tests/test_i18n.py`、`tests/test_langs.py` + **真窗口布局体检**（逐控件比 `reqwidth` / 实际宽，五种语言都来）；界面语言跟随系统 → 构造 GUI 的用例要**先钉死语言** |
| 模块拆分 / 函数签名变更 | `tests/test_wiring_signatures.py` + 全量；搬家的公共全局（如字体常量、`*_ctx` 同步表）要确认跟着改 |
| 新增/删除平台独占模块 | 两份禁列清单 + `check_platform_purity.py` + 模块对账 + [平台约束记录.md](../平台约束记录.md) 的清单 |
| 新增模块（任何一种） | `scripts/build_exe.py` 的 `HIDDEN`（按需导入的）+ [模块索引.md](模块索引.md) 重跑核对 |
| 采集 / 重采样 / 门限 | `tests/test_resample.py`（判据是相关性/主频，不是「跑通」）+ 真机回环脚本 |
| 手腕屏 / 桌面字幕 | 假对象单测 + `scripts/verify/` 对应脚本 + **改自愈阶梯时先跑旧路台阶那条用例** |
| 译音出声链 / 音量匹配 | `tests/test_level_match.py` + `tests/test_proxy_wiring.py`（译音出口的唯一性）+ 真机听感（只能人耳定） |
| 界面控件 / 布局 | 真窗口布局体检；设置窗按宽守卫（未映射也要可靠，别用「真显示设置窗」当 CI 守卫） |
| 更新链路 | `tests/test_update_check.py`、`tests/test_update_dialog.py`（注意历史残留，见 [踩坑索引.md](踩坑索引.md)） |
| 打包 / 发布 | `scripts/build_exe.py` + 产物自检三件套 + `scripts/verify_release.py` |

## 七、反「假绿」纪律（都是踩出来的）

1. **离线是硬要求**：新用例必须离线可跑（不许依赖网络 / 真设备）。抽查办法：
   套一个死代理（`HTTP_PROXY=http://127.0.0.1:1`）或断网跑一遍 —— 它红了就说明用例有隐藏的网络依赖。
2. **故障注入**：新增的守卫用例，**把修复点改回旧写法必须变红**。写完就注入一次；
   「代理说全过」不算证据。
3. **断言要钉住该级独有的行为**：自愈类用例只断言「碰巧出现了新对象」会假绿。
4. **状态类断言要卡在触发那一帧之后立即断**，多跑一帧会被「随后成功」把状态重置掉。
5. **全量测试一次只跑一份**：各用例共用 `out/` 沙箱与仓库根的 `config.yaml`，并发跑或被 kill
   会互相踩出假红。被 kill 的 run 还可能把 `update_ignored: [9.9.9]` 留在 `config.yaml` →
   更新弹窗那条用例从此永远红（表现为「有更新却没弹窗」）。判据：单独重跑全绿 = 假红。
6. **尺寸 / 几何类断言要按「它会在哪跑」写**：CI 的 Linux 腿跑在 `xvfb-run -a` 的**默认虚拟屏**上
   （本仓库**没有** `VLT_XVFB_SCREEN` 这类覆盖机制，别照上游那份写），所以几何类判据要么写成
   **相对关系**（控件之间的 reqwidth / 实际宽之比），要么把屏幕尺寸当**显式入参**传进去 ——
   别依赖宿主屏的实际分辨率。
7. **产物自检的判据是三件套**：退出码 0 + stdout 有 `GUI_SELFTEST_OK` + **本次**那份日志里也有
   （构建脚本末尾的判定可能读到上一份日志而误报）。
8. **推送到 GitHub 走 REST 脚本**（本机直连不可靠）：脚本推的是**已提交的 HEAD**，
   成功标志是 `byte-identical to local` + `content check: identical`；失败重试 3 次。
   ⚠️ 提交前先 `git add` 新文件 —— 否则它不在 local tree 里，推上去也没有。
