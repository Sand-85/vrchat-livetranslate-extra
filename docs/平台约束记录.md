# 平台约束记录

这份文档记录**不能改的硬约束**，以及每条约束背后的**实测依据**。

写它的原因：这些约束看起来都像「多此一举」——比如「虚拟声卡的 capture 侧不能用 `Audio/Sink`」，
不知道缘由的人（包括未来的我）会顺手改回去，然后制造一个**用户侧很难自己诊断**的故障：
系统声音突然没了、或者手腕屏把用户正在玩的 XR 应用搞乱。

所以每条都写清「**为什么**」和「**改回去会怎样**」。新增约束也照这个格式往下加。

---

## 一、音频：虚拟声卡绝不能用 `Audio/Sink`

**约束**：运行时声明虚拟声卡时，capture 侧（我们往哪写）必须是
`media.class=Audio/Sink/Internal`，**不能用 `Audio/Sink`**。

**依据**

WirePlumber 选「默认输出」时的候选类，精确等于：

```lua
-- /usr/share/wireplumber/scripts/default-nodes/rescan.lua:63-65
pushSelectDefaultNodeEvent (source, si_om, devices_om, "audio.sink", "in", {
  "Audio/Sink", "Audio/Duplex"
})
```

约束动词 `c` 是「属于其中之一」（精确匹配，不是前缀）。所以只要我们的类不在这两项里，
就**永远不可能被选成默认输出**。`Audio/Sink/Internal` 是 WirePlumber 自己在用的合法类
（bluez 设备集的内部成员节点，见 `monitors/bluez/create-set-node.lua:24`），不在候选列表里。

**改回去会怎样（实测事故）**

早期用 `Audio/Sink` 时，**一创建虚拟声卡，用户的系统声音就没了** —— WirePlumber
把我们的节点选成了默认输出，音乐/通话/游戏声音全被改道进虚拟设备。
实测时间线：创建后约 **1.8 秒**，`default.audio.sink` 变成 `vlt_mic_sink`。

**试过并且确认无效的「防护」**（别再走回头路）

| 办法 | 为什么无效 |
|---|---|
| `priority.session = 0` | **实测挡不住**。真实声卡是 696/1009/1109，我们 0，仍然被选中。根因至今没查清，所以**不能依赖它** |
| `node.virtual = true` | 默认选举**根本不看**这个属性（它只被 media-role 链接用） |
| `node.hidden` | **不存在**这个属性 |
| `node.disabled` | 只被 alsa / v4l2 / libcamera 这些**硬件 monitor** 读，普通节点无效 |
| `node.link-group` | 只有 `module-filter-chain` **注册过**的 smart filter 才被豁免（`is_filter_smart` 要求 link-group 已登记），`pw-loopback` 拿不到这条捷径 |

**相关：不要写配置文件、不要重启服务**

- **绝不**写 `~/.config/pipewire/**`。配置文件只在 daemon 启动时读，要生效就得重启
  PipeWire/WirePlumber —— 那会打断用户正在放的一切。
- **绝不**重启 pipewire / wireplumber。
- 所以一律走**运行时声明**：进程活着设备就在，进程退出立即销毁，全程不碰配置。

**麦克风侧可以参与默认选举**

用户明确的口径：虚拟麦就是**正常麦克风**，可以参与默认选举。所以我们不动 source 侧
（保持 `Audio/Source`），而且真实麦克风的 `priority.session`（2009/2100）本来就压过我们的 0。

**校验入口**：`tests/test_virtualmic_cable.py`（把这条钉死）、
运行时只读断言 `vlt/platform/linux.py: assert_not_default_output_candidate()`。

## 一之二、音频：Linux 只抓 VRChat 自己的输出流，绝不抓默认输出

**约束**：Linux 上「别人说话」这条腿的采集目标**只能是 VRChat 自己的音频输出流**；
找不到 VRChat 时**等待**，绝不回落到系统默认输出，也不回落到任何 sink。

**依据（实测，2026-09）**

VRChat（Proton/Wine）在 PipeWire 里的**播放输出是应用流节点**
`media.class = Stream/Output/Audio`，`node.name` / `application.name` = `VRChat.exe`
（同一进程会开 2 个输出流，都连到默认 sink）。它**不是** `Audio/Sink`。

因此 `query_loopback_devices()`（只列 `Audio/Sink`）**永远看不到 VRChat** ——
旧代码让用户在界面「VRChat 音频」下拉里选，候选全是物理输出设备（REDMI 音箱 / 内置音频 /
HDMI / `wivrn.sink`），靠关键词回退链去猜；点「自动检测」时实际抓的是**默认输出**。

实测该默认输出（`wivrn.sink`，WiVRn 串流）上同时挂着 VRChat、Google Chrome、vesktop、
`alsa_playback.wayvr` 等 —— 抓它等于把音乐、浏览器、系统提示音一起当成「游戏内语音」
喂给翻译模型。定向采集则干净（`pw-link -l` 可见只连到 `VRChat.exe:output_*`）。

**必须抓全每一路，且必须用 `object.serial` 定向**

- VRChat 会开**多个**播放流：实测同一次运行里有 `media.name` = `audio stream #1` 与
  `audio stream #5` 两个节点（后者当时 `pulse.corked=True`），可能各自承载一部分声音。
  只抓一路会丢声音 → 逐路各开一条 `pw-record`，用
  `vlt/platform/audio.py: MixedAudioSource` 相加限幅混成一路。
- 这些节点的 `node.name` **全部是 `VRChat.exe`**，按名字区分不了多个流；而
  `pw-record --target=` 的说明是「设置节点**目标序列或名称**」——
  传数字 node id 会被当成**名字**匹配，落空后**回落到默认目标**
  （实测 `--target=147` 没连到 147，而是连到了当时的 `vlt_mic_source`）。
  必须用 `object.serial`：实测 `--target=14061` → 精确连到 node 147、
  `--target=14002` → 精确连到 node 199。

**行为**

- 采集腿是「**等 → 采 → 流变化 → 再等**」的循环：VRChat 没跑就空转等待（状态栏/日志
  「等待 VRChat 音频输出」）；VRChat 中途退出、**或播放流增减**，都结束当前采集回到等待，
  重新启动/增流后自动接上。
- 不能只指望 `pw-record` 子进程退出 —— 目标节点消失后它**不会**退；所以采集循环每
  `VRCHAT_RECHECK_S`（3s）回查一次 PipeWire 图，比较 `serial` 集合：变了就收尾重开。
- **电平探针（设置窗里那条实时电平）必须复查同一个目标集合**：`vlt/level_probe.py`
  逐环复用采集腿的配方，所以同样会被 `pw-record` 的回落行为坑 —— 目标节点消失后
  session manager 按 `node.autoconnect` 把它回落到默认源（**麦克风**），探针会继续
  「看起来很正常」地出数，而那是麦克风的电平（用户照着它调门限就调错了）。
  探针因此也每 `VRCHAT_RECHECK_S` 复查一次 `serial` 集合（变了就关掉重开）；
  目标没了就关采集并每 5s 低频重试，读数回「—」（VRChat 再起自动接上）。
  校验入口：`tests/test_level_probe.py` 的 `test_recheck_*` / `test_open_failure_recovers_*`。
- 界面在 Linux 上只保留「麦克风」一个下拉；「VRChat 音频」/「译音输出」两个下拉隐藏。
  `capture.loopback_device` 与 `output.audio.device_name` 配置键保留但被忽略
  （Windows 侧照常生效）。

**校验入口**：`tests/test_vrchat_capture.py`（定位全部路 / serial 定向 / 不回落 / 混音 /
等待 / 流增减重开 全钉住）、`vlt/platform/linux.py: find_vrchat_output_streams()`、
`vlt/engine.py: pick_vrchat_targets()`、`vlt/platform/audio.py: MixedAudioSource`。

## 二、手腕屏：自建 OpenXR，不依赖第三方 overlay 管理器

**约束**：Linux 的手腕屏由**我们自己的进程**作为 `XR_EXTX_overlay` overlay session
直接连合成器，**不使用 WayVR 之类的外部 overlay 管理器**。

**依据**

这和 Windows 侧的结构**完全对等**：那边是 `openvr.IVROverlay().createOverlay()`，
我们的进程就是 SteamVR 合成器的直接客户端 —— 没有注册、没有配置文件、没有重启。

早期考虑过 WayVR，实测**它的自定义面板没有运行时注册接口**：

- `wayvrctl` / `wayvr-ipc` 的 19 条命令里**没有**「创建面板」（只有 `panel-modify` 改**已存在**面板的元素）
- `custom_panels` 只在 WayVR **启动时**从配置读（`wayvr/src/windowing/manager.rs:151`）
- **没有配置热加载**
- 它的 Wgui 面板 `_source=` 数据源只有 `clock` / `timer` / `battery` / `ipd`，**没有外部文本入口**；
  OSC 也是**只出不进**

⇒ 用 WayVR 就必须「写它的配置 + 重启它」，违反上面第一节同样的纪律。

**OpenXR 路线的实测结论**（`scripts/spike_openxr.py`，13/13 通过）

| 项 | 结论 |
|---|---|
| 图形绑定 | **按会话类型二选一**：Wayland → `XR_MNDX_egl_enable` + `GraphicsBindingEGLMNDX`；X11 → `XR_KHR_opengl_enable` + `GraphicsBindingOpenGLXlibKHR`。Monado 的 `oxr_session.c` 只分发 XLIB / WIN32 / ES_ANDROID / VULKAN / **EGL_MNDX** / D3D11 / D3D12，**没有 `OPENGL_WAYLAND_KHR`**（头文件里有类型常量，但运行时不实现） |
| 会话链 | `SessionCreateInfo → GraphicsBindingEGLMNDX → SessionCreateInfoOverlayEXTX`，`createFlags` 必须为 0（规范要求） |
| 前置调用 | 建 session **前**必须调 `xrGetOpenGLGraphicsRequirementsKHR`（Monado 检查 `sys->gotten_requirements`） |
| 会话状态 | 建完必须**泵事件到 READY** 再 `xrBeginSession`（`oxr_session_begin()` 首句就要求 READY） |
| 图层 | Quad ✅ + **Cylinder ✅**（弯曲可用）。⚠️ 柱面层的 `pose` 是**圆柱的轴**，与 Quad 的「面板中心」不同语义 —— 别照 Quad 那样摆位，见 §七 |
| swapchain | `GL_RGBA8 (0x8058)`；acquire 后必须 `wait_swapchain_image` |
| 锚点 | `/user/hand/{left,right}/input/grip/pose` **实测可追踪**；`tracker` 走 HTC role 路径（**未实测**）；`hmd` 用 VIEW 参考空间 |
| 锚点×位姿 | 位姿**按锚点分开存**（`overlay.offsets.<锚点>`，`overlay.offset` 只作兜底）：左右手 grip 坐标系沿 X 镜像、tracker 的挂点朝向随绑法变，共用一份 offset 等于「切一次锚点覆盖一份」，见第五节 |
| 动作集 | **只能 attach 一次**（再次调用 runtime **must** 报 `XR_ERROR_ACTIONSETS_ALREADY_ATTACHED`）；attach 后动作集 **immutable**（`xrCreateAction` / `xrSuggestInteractionProfileBindings` 同样报该错）。⇒ 要用几个锚点就**开局一次建全**，之后切锚点只换 space |
| 动作取名 | `actionName` 与 **`localizedActionName`** 在**同一个动作集内都必须唯一**（重复 → `XR_ERROR_NAME_DUPLICATED` / `XR_ERROR_LOCALIZED_NAME_DUPLICATED`）。实测：10 个动作共用一个 localized 名 → 只有第一个建得出来，其余锚点静默退回 VIEW（跟着头） |
| 建议绑定 | `xrSuggestInteractionProfileBindings` 对**同一个 interaction profile** 再次调用会**丢弃并替换**上一次的全部建议 —— 必须按 profile 聚合、**每个 profile 一次给全**。实测：逐个动作各调一次 → 每个 profile 上只剩最后一个动作的绑定（右手把左手覆盖掉），左手锚点永远 untracked |
| tracker 角色路径 | `/user/vive_tracker_htcx/role/...` 属扩展 `XR_HTCX_vive_tracker_interaction`：运行时没启用该扩展时 `xrStringToPath` 直接 `XR_ERROR_PATH_UNSUPPORTED`（没接 tracker 的 WiVRn/Monado 就是这样）⇒ 按**启用的扩展列表**判断整族建不建，别对着 8 个 role 各撞一次 |

**踩过的坑**（代码注释里也有，这里汇总）

1. **`xrPollEvent` 的结果必须从缓冲区起始强转**，不能从 `varying[]` 起 ——
   `EventDataBuffer{type(0),next(8),varying(16)}` vs
   `EventDataSessionStateChanged{type(0),next(8),session(16),state(24)}`，
   从 varying 读会偏 16 字节、读到垃圾 0（表现为「一个状态都没收到」）。
2. **`xrSyncActions` 在会话未 FOCUSED 时会抛 `XR_ERROR_SESSION_NOT_FOCUSED`** ——
   Monado 源码 `oxr_input.c` 明写「只能 focused 调」。而 overlay 会话要等合成器
   上报 visible/focused 才会进 FOCUSED。
   **早先这里没防，导致每一帧都在这一行夭折、`end_frame` 从未执行、手腕上什么都看不到。**
   正确做法：只在 FOCUSED 时同步，并且把同步失败当「本帧不同步」而不是「整帧作废」。
3. **`xrCreateReferenceSpace` 的第一个参数是 session，不是 instance** ——
   参数**个数**是对的，静态签名检查抓不到；报错信息也不指向具体行。
   现在由 `tests/test_openxr_overlay.py` 的句柄错配扫描守着。
4. **niri 的 X11/GLX 走不通是「特例」，不是 Xorg 的普遍情况**：niri 下 X11 是精简的
   `xwayland-satellite`，`glXChooseFBConfig` / `glXCreatePbuffer` 能过，但**所有**
   context 创建方式都被拒（`GLXBadFBConfig` / `BadValue`）。所以 niri 走
   libwayland-client + libEGL；真正的 Xorg 会话上 GLX 正常，走 Xlib 绑定
   （`XlibGlxContext`）。
   ⚠️⚠️ **GLX 的失败走 Xlib 异步错误通道，而默认错误处理器会直接 `exit(1)` 把整个进程
   带走**：实测在卫星上「只是建一次 overlay 的 GL context」，整个应用跟着消失。
   所以建上下文期间必须 `XSetErrorHandler` 接管（吞掉并记账）、`XSync` 把错误冲出来，
   再还原处理器 —— 见 `XlibGlxContext.__init__` 与 `tests/test_overlay_glx.py`。
5. **ctypes 的 `argtypes`/`restype` 必须写全** —— 不写的话 64 位指针被当 32 位 int 传，
   直接段错误（实测崩过）。而 `glXGetProcAddressARB` 要传**函数名字符串**，不是函数指针。

> ⚠️ **验证状态（2026-10）**：Wayland / EGL_MNDX 路径有真机验证（13/13 spike）；
> **X11 / XLIB 路径目前只有离线验证** —— Xvfb+GLX 下真实建上下文、binding 结构体、
> 后端选择（`tests/test_overlay_glx.py` + `tests/test_openxr_overlay.py`）；
> **真机（X11 显示 + 同一环境跑 Monado/WiVRn）验证仍是待办**。
> 验证入口：`python scripts/spike_openxr.py --gl x11`（或 `--gl-only --gl x11`）。

## 三、构建期平台隔离

**假设（用户口径）**：**Linux 上只用 OpenXR，Windows 上只用 SteamVR。**
不追求「一个平台同时支持两种 VR 运行时」——那需要把图形绑定也平台化，收益不抵成本
（详情与取舍见对话记录：Windows 侧 pyopenxr 的 D3D11 绑定确实可用，但真正卡住的是
`XR_EXTX_overlay` 只有 SteamVR 支持，而在 SteamVR 上本来就该用原生 overlay 接口）。

**约束**：Windows 产物里**不允许**出现 Linux 独占实现；反之亦然。
「反之亦然」这一半以前只写在文档里 —— **从未被验证过**（见下面「历史泄漏」）。

**做法**（四层，靠结构而不是靠纪律）

1. **模块边界**：平台独占实现各自独立成模块
   - Windows：`vlt/platform/win.py`、`vlt/output/openvr_overlay.py`（SteamVR 手腕屏后端）
   - Linux：`vlt/platform/linux.py`、`vlt/output/openxr_overlay.py`（自建 OpenXR 手腕屏）
   - **共享**：`vlt/output/overlay.py`（只有 `OverlayConfig` + 渲染函数，两端都收）
2. **共享代码不出现后端名字**：`engine.py` / `gui.py` 一律走工厂
   （`platform.create_wrist_overlay()` / `platform.open_audio_out()`），
   不直接 import 任何一侧的实现
3. **构建排除**（两侧都要做，**镜像操作**）
   - Windows：`scripts/build_exe.py` 的 `EXCLUDE_WIN` + `--exclude-module`
   - Linux：`scripts/build_appimage.sh` 的 `EXCLUDES` + `--exclude-module`
     （2026-10 起 AppImage 改走 **PyInstaller onedir**：代码进 PYZ、不再有明文
     `vlt/*.py`，所以排除也提前到分析期做 —— 旧路线那种「AppDir 里反向删 `.py`」
     已随路线一起退役。`tests/test_platform_purity.py` 会读脚本里的 EXCLUDES
     做一致性门禁：禁列清单改了、构建排除没跟上就红。）
4. **共享代码里的平台专有实现也要搬走**：`vlt/i18n.py` 曾自己调 Win32 的
   `GetUserDefaultUILanguage`（后果之一：**Linux 上界面语言恒定回落 "en"**），
   现在委派给 `platform.detect_ui_language()`。

**校验（两道）**

* `scripts/check_platform_purity.py` —— 解包产物、断言禁列模块与字样都不在。
  两种产物两条读取路径：exe 用 PyInstaller 的读取器解 PYZ（判据不是「搜 exe 原始字节」，
  单文件 exe 里的 PYZ 是 zlib 压缩的，直接搜永远搜不到）；AppImage 先
  `--appimage-extract` 解 squashfs，再找**内层可执行文件**（PyInstaller onedir 布局
  `usr/bin/<名>/<名>`）复用同一条读取路径。
  - 字样判据**只扫实现、不扫 docstring**：共享模块的 docstring 里要写「Windows 用 X、
    Linux 用 Y」的对照说明，那是文档不是实现。类体的 docstring 在 `co_consts[1]`
    （`[0]` 是类名），写错会把说明误判成实现。
  - 字样判据**只扫我们自己的实现**（`vlt.*` + 入口 `run_gui`）：第三方库本来就有
    跨平台内容（`sounddevice` 里躺着 PortAudio 的 `paWASAPI` 常量），拿平台禁列去扫
    第三方是假警；「第三方有没有混进来」由模块名判据负责（例如 Linux 侧禁 `openvr`）。
    这条口径与旧 AppImage 路线一致（它只扫 `usr/app`）。
* `scripts/verify_appimage.py` —— **独立验收脚本**（构建脚本第 6 步只是转调它，
  CI 也直接调它，不必重新构建）：① 平台纯度 ② 包内导入 + 反向排除 + xr 瘦身
  ③ 离线渲染一帧（**并断言「边距全透明 + 底板半透明」**，见 §六）④ Tk 中日韩字体可见
  （无显示器时明确标「跳过 = 未验证」，CI 里挂 `xvfb-run` 真跑）。
  - ⚠️ PyInstaller 布局下包里**没有独立解释器**，②③④ 由**产物自带的探针**
    （`vlt/selfcheck.py` 的 `--verify-imports / --verify-render / --verify-tk-fonts`，
    在 `run_gui.py` 最前面被拦截、进不去 GUI）执行；验收脚本只负责调用与判定。
    探针的返回码语义与旧版一致：0 通过 / 1 失败 / 2 跳过（环境原因）。
  - ⚠️ 旧版本的 ② 曾用「包内解释器 + `-P`」防误读仓库源码；探针做进产物后
    不再有这个坑（跑的就是打进包里的那份代码）。

**AppImage 路线与宿主依赖（2026-10 起）**

* 构建：PyInstaller onedir → xr 瘦身（平台目录由包内 pyopenxr 自报）→ AppDir → appimagetool
  （zstd L19 + 1M 块；比默认的 L15/128K 小 ~7%）。
* Tk：自编 `--enable-xft --disable-libcups` 版（见 §八）。
* **反向裁剪**：PyInstaller 默认把 ELF 依赖闭包全带进 `_internal/`，构建脚本删掉两组
  「机器上必然有」的库 —— X11 客户端栈、音频链路（portaudio/ALSA/JACK/PipeWire）；
  以及换 Tk 之后没人引用的 CUPS/GnuTLS 孤儿串。删完做两道断言：宿主 `ldconfig`
  真的能提供这些 soname、包内其余 ELF 的 `ldd` 没有 `not found`。
  运行机要求进 GUIDE.linux 前置条件（PipeWire / portaudio / 中日韩字体）。
* 保留在包里的：fontconfig/freetype/png/expat/brotli（字体渲染）、libstdc++/libgcc
  （numpy/OpenBLAS 的 ABI，不赌宿主版本）。

**历史泄漏（为什么这条以前形同虚设）**

* `check_platform_purity.py` 声称支持 `--platform linux` / AppImage，但实现只有
  PyInstaller 读取路径，**而且没有构建脚本或 CI 调用它** → Linux 侧从未被验证。
* 于是 `scripts/build_appimage.sh` 的「反向排除」只存在于注释里：
  **`vlt/platform/win.py` 一直被原样打进 AppImage**（连同 WASAPI/openvr 后端一起）。
  修好判据后第一次跑就抓到了，现在已修（该脚本后来整体换成 PyInstaller 路线，
  排除改成 `EXCLUDES`/`--exclude-module`，见上）。
* Windows 侧同样会红：共享的 `vlt/platform/base.py` / `__init__.py` 在 **docstring**
  里写了 `XR_EXTX_overlay` / `pyopenxr`，而文档字符串以前也算字样 → 这批改动一旦
  推上去 CI 立刻红灯。字样判据排除 docstring 之后才是对的。

**CI 与发布**：构建步骤在 `.github/workflows/appimage.yml` —— 一个**可复用 workflow**（
`uses:` 调用），因为同一份构建要出现在两个地方：CI（每次 PR / push main 防回归）与发布
（打 tag 时把 AppImage 当 Release 附件发出去）。放进一个文件是为了**只有一处**要维护：
系统依赖清单、Tcl/Tk 版本进 `actions/cache` 的 key、「构建 → 独立验收」的顺序 ——
抄第二份迟早只改一处。调用方：`ci.yml` 的 `appimage` job、`release.yml` 的 `appimage` job。
步骤本身：装依赖 → 构建 AppImage → `xvfb-run` 跑 `verify_appimage.py` → 上传产物（artifact）。

## 四、测试纪律：测试进程不许碰用户的运行时

**约束**：单元测试**不得**建立 OpenXR 会话、不得声明虚拟声卡、不得往真实音频设备播放/录制。

**为什么**：这两件事都是**连到用户正在用的系统上**的 ——
调试期间反复建/断 XR 会话会直接干扰用户当时的 OpenXR 应用；虚拟声卡会抢默认输出。
两条都出过事故。

**做法**

- 测试里把平台入口打桩（`platform.create_wrist_overlay` / `platform.open_audio_out`）
- 另有**结构性防呆**：`_test_process_guard()`（在 `vlt/platform/linux.py` 与
  `vlt/output/openxr_overlay.py` 各一份）—— `__main__` 在 `tests/` 下或名字以 `test_` 开头时，
  **直接拒绝**建立会话/声明设备
- 真机验证是**用户明确授权的单独一次**，不是「顺手跑一下测试」

**验证副作用是否为零**：

```bash
pw-dump | grep -c vlt_mic          # 应为 0
pgrep -a -x pw-loopback            # 应为空
```

## 五、配置语义两端一致

**约束**：`config.yaml` 里的 `anchor` / `offset.pos` / `offset.rot` / `width_m` /
`font_size` 等，**Windows 与 Linux 必须同义**。

**为什么**：用户在 Windows 上调好的角度（`rot: [-47, -16, 0]` 是作者实测的右手腕角度）
不该换个平台就废掉。

**具体到旋转**：两边都是「相对锚点的位姿」，
Windows 用 `setOverlayTransformTrackedDeviceRelative(device, matrix)`，
Linux 用 `CompositionLayerQuad.space + pose`。欧拉角约定都是 **`Rz · Ry · Rx`**，
Linux 侧换算成四元数时必须同序（由 `tests/test_openxr_overlay.py` 与独立的矩阵实现交叉验证）。

**左右手镜像**：左右手的 grip 位姿坐标系沿 X 轴镜像，所以 `rot` 要按下面的规则换算
（`Rz·Ry·Rx` 约定下）：`rx` 不变、`ry` 取反、`rz` 取反（位置的 `x` 分量同理）。

例：右手 `[-47, -16, 0]` → 左手 `[-47, 16, 0]`。（这是**起始值**，最终还是要戴着微调。）

**所以位姿按锚点分开存**：`overlay.offsets.<锚点>.pos/rot` 每个锚点各一套，
`overlay.offset` 退化为「该锚点还没单独存过」时的兜底（老配置只有这一份，照常工作）。
`vlt/output/overlay.py` 的 `resolve_offset()` 是这条口径的**唯一实现**，GUI 与两端后端
都从它取 —— 界面显示的位姿和面板真正用的那一份必须同源。
这条换算**只体现在模板的预设值里**（`config.example.yaml` 的 `left_hand` 那份），
代码不做自动换算：运行时替用户翻转角度，一旦某个 runtime 的手柄姿态约定不同，
面板会莫名其妙地歪，而用户无从判断是谁的错。

## 六、手腕屏：图层 alpha 必须显式声明两个 flag

**约束**：提交 composition layer 时必须带

```python
XR_COMPOSITION_LAYER_BLEND_TEXTURE_SOURCE_ALPHA_BIT | XR_COMPOSITION_LAYER_UNPREMULTIPLIED_ALPHA_BIT
```

（`vlt/output/openxr_overlay.py` 的 `layer_alpha_flags()`）。**Quad 与 Cylinder 两条分支都要带**。

**依据**

- 规范里图层**默认按 `alpha = 1.0` 合成** —— 不设 `BLEND_TEXTURE_SOURCE_ALPHA_BIT` 就等于声明
  「整层不透明」，贴图的 alpha 通道根本不参与。Khronos 官方 `hello_xr` 需要透明时正是加这两个 flag。
- 我们的贴图来自 PIL，是**未预乘**（straight）alpha，而运行时的默认假设是**预乘**，所以必须配
  `UNPREMULTIPLIED_ALPHA_BIT`：Monado 侧对应 `comp_render_helpers.h` 的 `is_layer_unpremultiplied()`，
  WiVRn 的 compute squasher 直接把 `unpremultiplied_alpha` 塞进 UBO。

**改回去会怎样（实测现象）**

面板蓝框外面多出一圈**不透明黑边**：贴图里 alpha=0 的 12px 边距 + 圆角外的三角区（占 7.5% 像素）
被当成实心黑画出来，底板自己的半透明（`bg_alpha`）也一起失效。
只少 `UNPREMULTIPLIED` 则是另一种错法：半透明像素偏亮、白字顶到 255（观感发白/发光）。

**校验入口**：`tests/test_openxr_overlay.py` 的 `test_layer_alpha_flags_value()`（flag 值）与
`test_composition_layers_declare_alpha_flags()`（**静态扫源码**：每处合成层构造都必须传 ——
Cylinder 那条漏了就是「换个曲率又冒黑边」这种半好半坏的状态）；
`scripts/verify_appimage.py` ② 还会断言**打进包里的那份代码** flag 正确。

## 七、手腕屏：柱面层的 `pose` 是「圆柱的轴」，不是面板中心

**约束**：`XrCompositionLayerCylinderKHR.pose` 描述的是**圆柱的轴（圆心）**，可见弧面在 pose
局部 **−Z** 方向、距原点 `radius` 处。所以摆位时必须把轴沿面板局部 **+Z** 挪 `radius`
（`layer_geometry()["pose_offset"]` + `rotate_vector()`），**不能**把 `cfg.pos` 直接当 pose。

**依据**

- 规范成员描述：`pose` 是 *"the center point of the view of the cylinder"*；`radius` = 圆柱半径；
  `centralAngle` = 可见段角度（对称展开在 0 rad 两侧）；`aspectRatio = 可见段宽/高`，
  且 `高 = (radius × centralAngle) / aspectRatio` ⇒ 可见段**弧长** = `radius × centralAngle`。
  另外概述里写明 *"the runtime must map a texture onto the inside of a cylinder section"*
  （曲面显示器那种凹面朝观察者）。
- Monado 的圆柱顶点着色器 `layer_cylinder.vert` 把几何写死为
  `a = (uv.x − 0.5) · centralAngle`、`x = sin(a) · radius`、`z = −cos(a) · radius`
  ⇒ 表面点满足 `x² + z² = radius²`、**轴过 pose 原点**、0 度处在 `z = −radius`。
  WiVRn 服务端走自己的 compute squasher（`layer.comp: do_cylinder`），圆柱求交用
  `axis = (0,1,0)` 与 `c = dot(o,o) − caoc² − radius²` —— **同一约定**。
- 弯曲度口径与 Windows 一致：`centralAngle = 2π · curvature`、`radius = width_m / centralAngle`
  （openvr.h 原文：`curvature = overlay.width / (2π·r)`）。**`width_m` 是弧长**，不是弦长
  （弯曲 0.5 = 180° 时弦长只有弧长的 2/π ≈ 64%）。

**改回去会怎样（实测现象）**

用户按宽度/角度摆好的面板会「圆心落在配置的位置、而面板整体沿局部 −Z 飘出 `radius` 远」——
0.23 m 宽的面板配 0.2 弯曲就是 18 cm 偏移（旧实现还带 `clamp(curvature*5, 0.2, 1.5)`，
半径最大能到 5× 面板宽，也就是飘出一米多）。反过来把 pose 当面板中心、只在几何上凑数的话，
弯曲时面板中点也不会停在原位。

**校验入口**：`tests/test_openxr_overlay.py` 的 `test_layer_geometry_matches_windows_curvature()`
（2π 口径 / 弧长 = 宽度 / `pose_offset`）与 `test_cylinder_pose_offset_rotates_with_panel()`
（偏移随面板 `rot` 旋转，且**弧面中点必须回到 `cfg.pos`**）。

## 八、Linux GUI 字体：Tk 必须认 fontconfig；「自带字体」是另一件事

**约束**

1. Linux 上跑图形界面时，进程里那份 Tcl/Tk **必须链了 Xft/fontconfig**，否则界面不是"难看"而是**直接废掉**。
2. 「GUI 能不能画中日韩」与「包里要不要自带中日韩字体」是**两个独立决定**。
3. **决定（2026-10）**：AppImage **不再打包任何字体**。中日韩字体一份 ~19MB，而系统普遍自带；
   为极少数没装字体的机器让所有人多背十几 MB 不划算。⇒ **运行机必须自带一套中日韩字体**
   （如 `pacman -S noto-fonts-cjk` / `apt install fonts-noto-cjk`），否则 GUI 与手腕屏都会缺字。
   即：第 1 条（Xft 版 Tk）照旧由构建期解决；第 2 条改成「由宿主机解决」。

**依据（实测，2026-10）**

| 观察 | 结果 |
|---|---|
| uv 独立 CPython 3.11 自带的 Tk | `ldd libtcl9tk9.0.so` **只链 libc/libdl/libm/libpthread**（X11 静态烤进去，无 Xft/fontconfig） |
| 同一台机的系统 Tk 8.6 | 链 `libXft.so.2` / `libfontconfig.so.1` / `libX11.so.6` |
| 字体族列表 | 无 Xft：**65 族 / 中日韩 0 个**、`TkDefaultFont` = `arial`、`measure("我说")` ≈ **400ms**；有 Xft：689 族 / 中日韩 65+、≈5ms |

为什么 uv 那份没有：python-build-standalone 的 `cpython-unix/build-tk.sh` **没传 `--enable-xft`**，
而 Tk 自己的 `configure.ac` 是「xft 默认 on，但靠 `pkg-config --cflags xft fontconfig` 探测，
探不到就静默降级」—— 那份构建镜像刻意最小化依赖（脚本里删掉 deps 的 `.so`、静态链 libX11），
于是探测失败，编出一个"只有 X11 核心字体"的 Tk。

**症状**：`resolve_ui_family()` 候选表一个都命不中 → 退到 `TkDefaultFont`（X 核心字体）→
控件按 `measure()` 算出的 `width=` 排好版却画不出字形 ⇒ 屏幕上**一排控件壳**（用户实测截图，
按钮/单选/复选/语言框的标签全空，只有 `chatbox`、`英语` 这类恰好有字形的能显示）。

**改回去 / 忽略会怎样（实测，都是"缺字体宿主"的模拟）**

- **只装了拉丁字体**（有 DejaVu、没中日韩）：GUI 标签全空；手腕屏更糟 ——
  `find_cjk_font()` 的 `fc-match …:lang=zh-cn` 会返回**不含中文的兜底字体**（实测拿到 `DejaVuSans.ttf`），
  于是渲染出**豆腐块**（中文全成空框、拉丁正常）。⚠️ 这同时暴露 `find_cjk_font()` 少了
  一道「返回的字体真的覆盖中日韩」的校验（应改用 `fc-list :lang=zh-cn`，拿不到就返回 None 走位图兜底）。
- **一个字体都没有**（Arch 最小安装）：**Tk 直接起不来**
  （`TclError: … failed to allocate font due to internal system font engine problem`）。
  ⇒ 这正是「AppImage 要不要自带 NotoSansCJK」争议的由来：自带的话，它一次兜住 GUI 与手腕屏两条腿；
  **但 2026-10 起我们选择不带**（拿体积换普遍性），改成要求运行机自带中日韩字体。

**两件事的分工**

| | 解决什么 | 谁在做 |
|---|---|---|
| Xft 版 Tk | 让 Tk **看得见** fontconfig 里的字体 | AppImage（2026-10 起 PyInstaller 路线）：构建期**自编** `--enable-xft`（且 `--disable-libcups`，见下）的 `libtcl9tk9.0.so`，`--add-binary` 注入；**源码运行：待补（`setup.sh` 自检 + 修复）** |
| 打包 NotoSansCJK | 保证机器上**存在**可用的中日韩字体 | **已取消**（2026-10）：AppImage 不再打包任何字体，改为**要求运行机自带** |

**PyInstaller 路线（2026-10 起已是官方打包路线）**

PyInstaller 不提供 Tcl/Tk，它把**当前解释器**的 Tcl/Tk 当文件收进包
（onedir：`_internal/libtcl9.0.so` + `_internal/libtcl9tk9.0.so` + `tcl9/`、`_tcl_data/`、`_tk_data/`；
onefile：进归档）。带不带 Xft **只由那一个 `libtcl9tk9.0.so` 决定**：

| 实验 | 结果 |
|---|---|
| 换入无 Xft 那份 | 65 族 / 中日韩 0 / measure 491ms（复现故障） |
| 换回 Xft 那份（onedir 下**一行 `cp`**） | 689 / 68 / 5ms |
| onefile：解释器里是**坏**的，构建时 `--add-binary <Xft 版>:.` | 产物 689 / 68 / 5ms（归档里只剩一份，即 Xft 版） |

⇒ 构建脚本的做法是「**自编**一份同版本、`--enable-xft --disable-libcups` 的 Tk，
用 `--add-binary` 顶掉解释器自带的那份」（缓存按 Tcl/Tk 版本分目录），构建后断言
「必须链 Xft、必须不链 CUPS」。Windows 侧不适用：Tk 在 Windows 走 GDI/DirectWrite，
不经 fontconfig。

⚠️ **为什么还要 `--disable-libcups`**（2026-10 实测）：Tk 的 Unix 构建默认
`--enable-libcups`，于是 `libtcl9tk9.0.so` 硬链 `libcups` ⇒ 顺着
`libcups → libgnutls → p11-kit/nettle/gmp/unistring → avahi/dbus/systemd`
拖进 **14 个库（解压 11.8MB / 压缩 ~4.6MB）**，而我们从不打印。
关掉后这些库从源头消失（构建脚本另有一步「清孤儿」：PyInstaller 是按**解释器自带
的带 CUPS 的 Tk** 分析依赖的，换 Tk 后那串库成为无人引用的死重，要显式删掉）。

**校验入口**

- 现成：`scripts/verify_appimage.py` ④「Tk 中日韩字体可见」——⚠️ 它验的是**宿主机**的字体
  （`fc-list :lang=zh`），跑在有字体的宿主上**必然通过**，所以**抓不到「产物缺字体」**这类退化。
  由于 AppImage 已不再自带字体，「宿主机没装中日韩字体」现在按**跳过 = 未验证**处理（不判红），
  只有「宿主机有、Tk 却看不见」才判红（那才是 Xft 版 Tk 坏了）。
- 待补（运行期，比构建期更该有）：GUI 启动前 / 手腕屏各一条「中日韩族数为 0 / 一个字体都没有」的
  明确提示；以及上面那条 `find_cjk_font()` 的覆盖校验。

## 九、桌面字幕：Wayland 走原生 layer-shell、X11 走原生 ARGB；拖动必须双源（Wayland）

**约束**

1. **Wayland 会话的桌面字幕优先自己开原生 `wl_surface`**（`zwlr_layer_shell_v1` +
   `wl_shm` ARGB8888 预乘出图）—— Tk 经 XWayland 做不到逐像素透明/自定位/协议级穿透。
2. 合成器能力**运行时探测**（有没有 `zwlr_layer_shell_v1`），没有就回落 Tk
   （GNOME/Mutter、Weston）；`desktop_overlay.backend` 可强制
   （`auto | native | tk | wayland | x11`）。
3. **拖动双源**：relative-pointer 优先（sway/wlroots 系第一帧就有增量）；niri 系
   **不发**相对位移事件 —— 80ms 观察窗后自动切「本地坐标法」：
   `新位置 = 锚点位置 + (wl_pointer.motion 本地坐标差)`。
4. **测试进程不许建原生窗**（会连到用户正在用的合成器）；真协议验收直连**私有嵌套
   headless sway** 并注入虚拟指针。防呆在 `vlt/platform/linux.py:_test_process_guard`。
5. **多屏位置必须读 xdg-output**（`zxdg_output_manager_v1` 的 `logical_position` /
   `logical_size`）：wlroots 系（sway/Hyprland）的 `wl_output.geometry` x/y **恒为 (0,0)**，
   拿它挑输出会认错屏、边距也算错；niri/smithay 两者都对，但统一走 xdg-output、
   geometry 只作兜底。
6. **跨屏拖动**：拖动过程中面板夹在本输出边缘（换面会打断指针 grab），**松开时按落点
   自动重建面到指针所在输出**；拖动全程平滑跨屏跟手属后续项。
7. **X11 会话走原生 32 位 ARGB 覆盖窗**（`vlt/platform/x11.py`）：`XMatchVisualInfo(32,
   TrueColor)` + 预乘 `XPutImage`（与 Wayland 后端同一份 `overlay_pixels` 像素）；
   穿透 = X Shape 输入区（复用 `linux.set_click_through`）；逐像素混合需要合成器 ——
   `_NET_WM_CM_S<n>` 无主时**自动降级**：每帧按面板 alpha 裁 1 位形状蒙版（黑框消失，
   圆角变锯齿、底板实色；有合成器时不裁，保持圆润 alpha）。
8. **X11 建窗必须 `background_pixel=0 + border_pixel=0`**（`CWBackPixel|CWBorderPixel`）——
   `background_pixmap=None`（`CWBackPixmap`）建 32 位窗实测 `BadMatch`（与父窗 24 位底的
   深度冲突）。
9. **XImage 的像素缓冲必须自备**：`XCreateImage(data=NULL)` **不会**分配数据（实测
   `data` 是空指针）；自备缓冲后**禁止 `XDestroyImage`**（会把 Python 的内存 free 掉），
   释放只 `XFree` 结构体。字节序必须 `LSBFirst`（小端 BGRA 预乘），不符直接拒绝。
10. **X11 拖动用绝对坐标 + `XGrabPointer`**：`新位置 = 抓取时窗口位置 + (x_root/y_root
    位移)`，不需要 Wayland 那套双源；拖动全程自由跨屏（X11 没有「面必须属于某块输出」的
    协议约束），也没有「松手换面」这一步。
11. **Tk 回落路径在 Linux 上用 1 位形状蒙版抠底**（`overlay_pixels.alpha_mask_bits()` →
    门面 `set_window_shape`）：Tk 没有 `-transparentcolor`（Windows 专属），面板圆角外的
    键色底只能靠 `XShapeCombineMask(Bounding)` 抠掉；蒙版 = 面板自身 alpha、默认阈值
    **32**（128 会误裁 `border_alpha=120` 的边框与低透明度底板）、每行 `ceil(w/8)` 字节
    LSB-first。**不乘整层 alpha**（乘了会在低透明度时把整个窗裁没；整层透明度由
    `-alpha`/`_NET_WM_WINDOW_OPACITY` 统一做）。逐像素半透明做不到，那是原生窗的能力。

**改回去 / 忽略会怎样**

- 只认 relative-pointer：**niri 上拖不动**（用户 bug 根因：按下/松开都收到、落点纹丝不动；
  调回旧行为会复发）。
- 拿 Tk 窗跑 niri：不透明矩形 + 被平铺管理（issue 原文现象）。
- 不用 xdg-output：sway/Hyprland 多屏下会**认错屏**（边距按 (0,0) 算）。
- 不给测试防呆：测试会去连用户正在用的合成器建窗。
- X11 上用 `background_pixmap=None` 建 32 位窗：直接 `BadMatch`（没有原生腿）。
- 用 `XDestroyImage` 释放自备像素缓冲：free 到 Python 的内存（实测踩过段错误）。
- 无合成器时不提醒：用户会以为「透明坏了」，其实起个 picom 就好。
- Tk 回落不做形状蒙版：Linux 上圆角外一圈键色底（不透明矩形）——就是 issue 的原始观感。
- X11 无合成器不做形状蒙版降级：透明区一圈黑框（用户实测报过，见上表）。
